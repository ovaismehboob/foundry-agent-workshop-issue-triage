# Evaluation dataset - schema notes

`dataset.jsonl` is a **JSON Lines** file: one JSON object per line. The Foundry portal evaluation wizard accepts **CSV or JSONL** datasets (a single JSON array file isn't supported), so the lab uses JSONL. Each line is still plain JSON that you can read and edit.

The file is generated by [scripts/build_eval_dataset.py](../scripts/build_eval_dataset.py) from the synthetic issues in `app/data` and the expected labels in that script. Don't edit `dataset.jsonl` by hand; change the script and run it again. `tests/test_evaluation_dataset.py` fails if the file is out of date.

## Fields

| Field | Used by | Description |
|---|---|---|
| `query` | Portal (`{{item.query}}`), local scorer | The exact message sent to the agent. It uses the CLI prompt format and includes customer context, because the portal Prompt Agent has no customer lookup tool. |
| `ground_truth` | Portal (optional mapping) | Expected category, priority, team, known incident, and a short note about what a good answer contains. |
| `id`, `issue_id`, `case_type` | People, local scorer | Record ID, source issue, and case type: `straightforward`, `grounded`, `context`, `ambiguous`, `unsupported`, `safety`. |
| `expected_category`, `acceptable_categories` | Local scorer | Exact labels. Ambiguous cases accept more than one value. |
| `expected_priority`, `acceptable_priorities` | Local scorer | Exact labels. |
| `expected_team` | Local scorer | Derived from `app/data/routing_rules.json`. |
| `expected_known_issue_id` | Local scorer | `KI-xxxx` when the knowledge base should link the issue to a known incident, otherwise `null`. |
| `channel`, `customer_id`, `message` | Local scorer | Used to rebuild the issue for the local engines. |

In the portal field-mapping step (single-turn evaluation), map **query** to `query` and **ground_truth** to `ground_truth`. The agent produces the **response** during the evaluation run. Extra fields are ignored by the portal.

## Case coverage
- 22 records: 20 from `app/data/incoming_issues.json` plus 2 extra cases (a direct prompt-injection attempt and a question that the knowledge base can't answer).
- Includes straightforward, grounded, context-dependent, ambiguous, unsupported, and safety-related cases, plus one Arabic message.

## Why there are two kinds of scoring
- **Portal evaluators** (for example Intent Resolution, Task Adherence, Relevance, Coherence, and the safety evaluators) use a judge model to rate response quality.
- The **local scorer** (`scripts/score_triage.py`) checks the business labels exactly: category, priority, routed team, and known incident ID. The built-in portal evaluators don't do exact label matching.
